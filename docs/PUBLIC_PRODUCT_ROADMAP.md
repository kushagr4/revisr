# Revisr public product roadmap

Updated 11 October 2026 during source-level continuation on `codex/ios-completion`. The Phase 0 inventory below describes the pre-foundation baseline; later phase sections record the current implementation. This document does not grant redistribution rights or change the private release status.

## Phase 0: baseline inventory before public foundation

- SwiftUI/SwiftData iOS 17 app, local-first, five admissions tabs (Today, Plan, Progress, Topics, Settings). `RevisrApp` opens a persistent `ModelContainer`, then `SeedDataService` imports bundled admissions, solution and programme manifests. PDFKit resolves local papers and solutions. AVKit plays locally bundled solution videos.
- The catalogue manifest currently contains 2,600 questions and 136 sources. The solutions manifest has 120 documents and 2,364 links. The programme migration contains 30 days; a fresh run of the historical seed path has 894 stored assignments, 452 active. The Resources tree contains 234 PDFs and 8 MP4s. These source counts agree with the September release-candidate audit; runtime store counts still need verification after a successful device or simulator run.
- The 30-day `TMUA-30-DAY-2026` programme is a personal plan. `AppSettings` defaults include a 16 October 2026 exam date, 22 August 2026 start date, 2,040 weekly minutes, unavailable Thursdays/Sundays and a Tuesday 14:00 start. `SeedDataService` forces TMUA active, and `AdmissionsImportService` imports the personal programme with catalogue data. Thus a clean install currently receives somebody else's schedule, though it receives no attempt history.
- Existing SwiftData models preserve question/source IDs, attempts, completed work and historical subject data. Programme migration retains attempted assignments and deactivates obsolete untouched assignments. Existing tests cover migration, catalogue and solution mapping, protection and relaunch; several use the historical seeding path as a fixture.
- Canonical preparation streams include TMUA, SMC and BMO, but the persisted `AdmissionsTestKind` and profile manifest only expose TMUA/CSAT. SMC and BMO have question content, not verified public onboarding, scoring, diagnostic-paper selection or scheduling policies. BMO needs marks or self-assessment rather than binary correctness.
- Source metadata has names, families, years for some papers, local filenames and checksums. It has no complete licence, permission, authoritative source URL or required attribution fields. Solution documents record provenance organisations, but none of the eight bundled video records has an original channel URL. The PDFs total 115,451,949 bytes and MP4s 329,716,387 bytes. Public distribution and in-app video replacement require a source-by-source rights/provenance audit.
- Xcode 26.6 is installed. The first sandboxed build could not compile assets because CoreSimulatorService was inaccessible. Unsigned generic iOS Debug and Release builds passed with Xcode service access. An iOS 26.5 simulator is available for tests. No new cold-launch or memory measurement has been taken; the September audit's performance observations are historical.

## Architecture and staged work

### Phase 1: public-user foundation

Separate catalogue import from the personal programme import at app bootstrap. Identify legacy stores before creating new settings; keep their programme and historical data. Give clean stores an explicit onboarding state and neutral study-availability defaults. Persist the selected TMUA/SMC/BMO stream, exam date, weekly target and unavailable days. Keep the legacy `AdmissionsTestKind`, import IDs, protection rules and bundle identifier stable. Show a new-user setup surface and an honest diagnostics-pending state; do not show the personal 30-day plan to a new user.

Acceptance: fresh persistent store has no personal programme/assignments, attempts or sessions; reopening preserves onboarding choices and still has no personal programme; a legacy fixture retains attempts, completed assignments, dates and migration behaviour; catalogue and solution counts/IDs remain stable. Test TMUA default and all three stream choices. A clean-store onboarding profile must not imply that a personalised plan exists.

Foundation slice implemented: app launch distinguishes clean and legacy stores; catalogue import can omit the personal programme; clean onboarding saves examination, date, weekly target and available weekdays locally. The legacy five-tab experience and historical seed/migration path remain available to existing stores. Phase 2 now continues the new-user screen into diagnostics. Generated scheduling, public rights clearance and refreshed main tabs remain later phases.

Verification on 9 October 2026: the full Swift simulator suite ran 134 tests with 0 failures and 6 skipped tests whose historical `.qa` store fixtures are absent. Five new foundation tests passed, including clean catalogue import, no personal plan, a saved BMO profile across persistent-store reopen, legacy attempt preservation and distinct assessment styles. Unsigned Debug and Release generic iOS builds passed. The clean setup screen was launched and visually checked on a newly created iPhone 17 Pro simulator (iOS 26.5). Actual old-schema/device-store migration, diagnostic usability and performance remain unverified in this checkout.

### Phase 2: two-paper diagnostics

Implemented in the development build: the clean-user setup leads to a two-paper diagnostic home for TMUA, SMC or BMO. The fixed, exam-specific selection is checked against active bundled PDFs, complete numbered question/page references, stream eligibility, usable/unprotected status, duplicate metadata and distinct IDs. TMUA and SMC also require a verified local PDF solution linked to every selected question. An unavailable or changed resource stops the workflow with a visible content issue instead of substituting another paper. See `DIAGNOSTIC_CONTENT_AUDIT.md` for the six selected sources and verified conventions.

SwiftData now stores an exam-scoped assessment, two paper records and one response record per question, with stable identifiers, stage and timestamps, elapsed time, locked answer/submission state, marking provenance, BMO proof/notes/estimated marks and completion. New drafts never become historical `QuestionAttempt` rows. The UI supports PDF question navigation, elapsed timer and pause, saved answers, submission confirmation, locked self-marking, completed-paper summaries, a second-paper gate and a final report. The timer pauses when leaving the assessment or when the app goes inactive; after an abrupt interruption, reopening stops an orphaned timer without adding unverified offline time. Switching examination keeps prior diagnostic history, and reopening the original examination restores it.

TMUA has two 20-question Euclid mock papers, each 75 minutes. The score is a count of user-confirmed correct answers, not a scaled TMUA score. SMC has distinct UKMT 2023 and 2024 papers, 25 questions and 90 minutes each; user-confirmed marking permits the verified 25-start, +4/−1/0 point calculation. BMO1 has two UKMT papers, six written-proof questions and 210 minutes each. Its 0–10 marks are explicitly self-estimated; no examiner mark or invented rubric is shown. No structured verified answer keys exist for these sources, so automatic scoring is unavailable.

The report presents per-paper results, unanswered/unassessed coverage, topic and reasoning-skill signals. Strong difficulty requires at least four assessed questions across both papers, at least three misses and an ordinary-difficulty miss; one wrong answer never declares a topic weak. Smaller samples show possible improvement or insufficient evidence. BMO subjective marks cannot produce a strong-difficulty claim. Reliable elapsed time is shown per paper; timing by topic/question is not inferred.

Functional acceptance: the complete two-paper TMUA path was walked in an isolated iOS 26.5 simulator, including PDF access, saved draft/resume, lock before PDF solutions, self-marking, second-paper unlock and final report. Automated persistent-store tests cover relaunch and all three exam policies, including SMC scoring and BMO self-estimated marks. The final full Swift simulator suite passed 142 tests, 0 failures, with the same 6 skipped historical `.qa` fixtures; unsigned generic iOS Debug and Release builds passed. BMO marking remains a documented self-assessment limitation because no verified local solution or mark scheme is bundled. Public distribution remains gated on rights clearance. No physical-device verification was performed.

Acceptance: two verified, nonduplicated papers per supported exam or a clearly disclosed content gap; interrupted diagnostics resume; topic performance uses only assessed evidence; protected questions and benchmark rules remain enforced.

### Phase 3: adaptive programme

Implemented in the development build. `PublicPlanningEngine` is a pure, value-only deterministic allocator. It takes the selected examination, exam date, weekly minutes, available weekdays, diagnostic evidence, recent outcomes, eligible catalogue questions and complete-paper candidates. It produces stable dated tasks with bounded per-day capacity, topic priorities, error review, targeted practice, consolidation, mixed work, timed work, final review and occasional complete-paper tasks when an exact paper is available. Every generated task carries a human-readable reason grounded in diagnostic evidence or the selected planning policy.

Public programmes and tasks use separate stable IDs from the imported private programme. `PublicProgrammeService` stores programme snapshots and task completion in SwiftData, preserves attempts and completed tasks, freezes the next three calendar days during refresh, and rebuilds only future incomplete work when settings change. A clean-user diagnostic completion now leads to Today, Plan, Progress, Topics and Settings views. Today shows the current workload and completion state; Plan explains the calendar and refresh behaviour; Progress counts completed tasks and recorded outcomes; Topics shows the evidence-based priorities; Settings exposes the saved preparation choices and privacy boundary. Question tasks record an outcome, minutes and notes as a `QuestionAttempt` with programme origin. Full-paper tasks are recorded as completed work without inventing a score.

The allocator treats the exam date as an exclusive boundary, excludes unavailable days and protected/legacy assignments, avoids duplicate question IDs, and fails with an explicit error when no day or usable capacity exists. Diagnostic rows that were not assessed are excluded from fresh practice; wrong, partial or review-flagged evidence can return as error review. BMO review uses the user's self-assessed mark as a partial signal and does not claim examiner scoring.

Verification on 9 October 2026: the deterministic engine and programme service tests passed 8/8, covering repeatability across 7/30/90-day windows, date boundaries, weekday capacity, unavailable days, diagnostic prioritisation, error review, daylight-saving dates, persistent relaunch, completed-task preservation, refresh behaviour and all three examination policies. The full two-paper diagnostic flow was completed before programme generation, and an isolated iOS 26.5 simulator walk-through visibly verified programme creation, one completed question, Today progress (1/5), Plan calendar counts and Progress outcome/topic counts. A final full-suite and generic Release rerun was blocked by CoreSimulatorService becoming unavailable; the existing Phase 2 full suite remains recorded as 142 tests with 0 failures and 6 skipped historical fixtures. Public source rights and solution redistribution remain unresolved; local catalogue resources continue to be labelled development content pending rights review.

Acceptance: repeat inputs yield identical schedule and rationale; short/long windows, rest days, missed sessions and insufficient coverage have bounded, understandable results; no mandatory day exceeds the stated time budget; regeneration cannot change completed or historical work.

## Current risks and decisions needed later

- The current imported catalogue includes material with unverified public redistribution rights. Attribution alone does not establish permission.
- The diagnostic uses audited source eligibility and verified paper-level conventions, but no structured answer keys. TMUA/SMC results depend on honest user marking; BMO results are self-estimates without a bundled mark scheme. The public release remains gated on source and solution redistribution rights.
- Existing views select the first active admissions programme and include TMUA-specific wording. They must be scoped to the selected generated programme before the new user enters the main five-tab experience.
- The six historical `.qa` fixture tests are still skipped because their fixture stores are absent. Do not claim full old-schema migration verification until those stores are supplied and the tests run.
- The Phase 3 programme uses conservative estimated minutes (TMUA 15, SMC 12, BMO 45 per question) and deterministic allocation; it is a planning aid, not an official timing or score model. Complete-paper scheduling appears only when the local source has an exact question count and an eligible paper-level resource.
- The isolated simulator walk-through used local development PDFs whose rights are still pending review. No physical iPhone was changed and no public bundle or distribution upload was made.
